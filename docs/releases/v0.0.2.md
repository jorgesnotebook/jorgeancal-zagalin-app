# Zagalin v0.0.2 - Security & Governance

**Release Date**: December 27, 2025

## 🎯 Release Theme: Security & Governance

Zagalin 0.0.2 transforms the plugin from a proof-of-concept into a production-ready observability assistant trusted by enterprise teams. This release introduces comprehensive security controls that make it safe to deploy in environments with strict compliance requirements, multiple teams, and sensitive observability data.

Every query now flows through a six-step security pipeline that validates, governs, and audits all interactions. Administrators gain fine-grained control over datasource access, query complexity, and OpenTelemetry compliance. Teams can now confidently enable AI assistance across their entire organization without compromising security or data governance.

Whether you're managing a multi-tenant Grafana instance, enforcing OpenTelemetry standards, or need comprehensive audit trails for compliance, Zagalin 0.0.2 provides the guardrails you need while keeping the user experience frictionless.

## 🚀 What's New

### Major Features

#### Query Validation System
Protect your observability stack from malicious or expensive queries with pattern-based validation for PromQL, LogQL, and TraceQL.

**Key capabilities**:
- Syntax validation with balanced braces and operator detection
- Complexity scoring prevents expensive queries (configurable max complexity)
- Function allowlists for PromQL (e.g., only allow safe aggregation functions)
- SQL injection pattern detection (UNION SELECT, DROP TABLE, etc.)
- Two enforcement modes: strict (reject) or sanitization (attempt to fix)
- Independent toggles for each query language (PromQL/LogQL/TraceQL)
- Comprehensive audit logging with violation types and user context
- Zero external dependencies (manual pattern matching, small binary)
- >90% test coverage

**Why it matters**: Organizations can now safely enable LLM-powered query generation without risk of injection attacks or runaway queries that could impact production observability systems. The validation is fast (pattern-matching, no AST parsing), reliable, and provides detailed error messages to help users fix issues.

#### OpenTelemetry Scope Enforcement
Automatically inject `service_name` and `deployment_environment_name` labels into all queries, ensuring OTel compliance across your organization.

**Key capabilities**:
- Enforces service and environment labeling in PromQL, LogQL, and TraceQL
- Configurable defaults per organization
- Scope extraction preserves user-specified values
- Two enforcement modes: full enforcement (reject non-compliant) or validation-only (warn)
- Seamless integration with existing queries
- Audit logging for all scope enforcement actions

**Example transformation**:
```promql
# User writes
rate(http_requests_total[5m])

# Zagalin enforces
rate(http_requests_total{service_name="my-service",deployment_environment_name="production"}[5m])
```

**Why it matters**: Organizations adopting OpenTelemetry standards can now enforce compliance automatically. No more manual reviews of queries or inconsistent labeling. Every metric, log, and trace query will include the required scope labels, making correlation and troubleshooting reliable across your entire observability stack.

#### Datasource Governance
Control which datasources users can query through allowlists, preventing accidental access to dev/staging data from production dashboards.

**Key capabilities**:
- Restrict queries to approved Prometheus/Loki/Tempo instances
- Per-organization datasource control
- Default datasource fallback
- Automatic datasource type detection (Prometheus, Loki, Tempo, Mimir, Cortex, Jaeger)
- Audit logging for blocked access attempts

**Why it matters**: In multi-environment setups, accidentally querying dev metrics from a production dashboard can lead to confusion and wasted time. Datasource governance ensures teams always query the right data sources and provides visibility into any unauthorized access attempts.

#### Conversation History Management
Persistent conversation storage with dual-tier architecture (backend file storage + localStorage fallback) and automatic migration.

**Key capabilities**:
- User-isolated file-based backend storage
- Full CRUD operations (Create, Read, Update, Delete)
- Pin favorite conversations
- Automatic title generation from first message
- Manual title editing with inline editor
- Context preservation (dashboard, panel, time range)
- Metadata tracking (message count, last preview, timestamps)
- Automatic migration from localStorage to backend
- Bulk deletion with confirmation modals

**Why it matters**: Users can now build on previous conversations, creating a knowledge base of troubleshooting sessions and investigation patterns. The dual-tier storage ensures conversations are never lost, even when the backend is unavailable.

#### Six-Step Security Pipeline
Every query flows through a comprehensive security pipeline that protects your observability infrastructure.

**Pipeline stages**:
1. **Authentication**: Extract user identity (user ID, org ID, email) from Grafana context
2. **Rate Limiting**: Token bucket algorithm (60 req/min default, configurable)
3. **Datasource Allowlist**: Verify datasource is approved
4. **Query Validation**: Pattern-based injection prevention and complexity limits
5. **OTel Scope Enforcement**: Inject service_name and deployment_environment_name
6. **Query Execution**: Forward to Grafana with full audit trail

**Why it matters**: Defense in depth. Each layer adds protection, and together they provide comprehensive security without sacrificing user experience. Every interaction is logged with full user context for compliance auditing.

### Developer Experience Improvements

#### AI Development Tools
Standardized configurations for Claude Code, ChatGPT, GitHub Copilot, and Cursor AI make AI assistants immediately productive.

**Key capabilities**:
- `.claude/CLAUDE.md` (500+ lines): Complete architecture reference, security checklists
- `.openai/INSTRUCTIONS.md`: Copy-paste ChatGPT instructions
- `.github/copilot-instructions.md`: Auto-loaded by Copilot
- `.cursorrules`: Cursor AI configuration
- KISS development philosophy documented
- Security-first approach emphasized

**Why it matters**: New contributors (human or AI) can understand the codebase architecture, security patterns, and development philosophy in minutes instead of days. AI coding assistants become context-aware teammates rather than generic code generators.

#### Local CI Pipeline
Run the full CI pipeline locally before pushing with `ci-local.sh` and pre-commit hooks.

**Key capabilities**:
- Single script runs: typecheck → lint → test → build → backend tests → plugin validation
- Pre-commit hooks prevent broken commits
- Catches issues before CI/CD (saves time and CI minutes)
- Skip with `git commit --no-verify` when needed

**Why it matters**: Faster feedback loop. Developers catch TypeScript errors, lint issues, and test failures locally before pushing, reducing cycle time and keeping the main branch green.

#### Privacy-Conscious Usage Logging
Track usage analytics without exposing sensitive query content or user messages.

**Key capabilities**:
- Signal type detection: metrics, logs, traces, dashboard, investigation, general
- Detects from dashboard context and message keywords
- Never logs query content or message text
- Only logs: user, org ID, signal type, message length, dashboard presence
- Enables product analytics without privacy violations

**Why it matters**: Product teams can understand usage patterns (what signals users query, which skills are used most) without accessing sensitive data. Compliance teams can audit access without exposing queries.

## ⚙️ Configuration Changes

### New Settings

All security features are opt-in and disabled by default:

```json
{
  "queryValidation": {
    "enabled": false,                    // Master switch for all validation
    "enablePromqlValidation": false,     // Toggle PromQL validation
    "enableLogqlValidation": false,      // Toggle LogQL validation
    "enableTraceqlValidation": false,    // Toggle TraceQL validation
    "strictMode": false,                 // true = reject, false = sanitize
    "maxQueryComplexity": 50,            // Max complexity score
    "allowedFunctions": [],              // PromQL function allowlist (empty = all)
    "logValidationAttempts": true        // Log all validation events
  },
  "otelEnforcement": {
    "enabled": false,                    // Master switch
    "requireServiceName": true,          // Enforce service_name label
    "requireEnvironmentName": true,      // Enforce deployment_environment_name
    "defaultServiceName": "unknown",     // Default if not specified
    "defaultEnvironmentName": "unknown", // Default if not specified
    "rejectIfNoScope": false,            // true = reject, false = inject defaults
    "validationOnlyMode": false          // true = warn only, false = enforce
  },
  "allowedDatasources": [],              // Empty = all allowed
  "defaultDatasource": ""                // Default datasource UID
}
```

### Recommended Settings

**For Development**:
```json
{
  "llmBackend": "grafana-llm-app",
  "maxRequestsPerMinute": 120,          // Higher limit for dev
  "queryValidation": {
    "enabled": true,
    "strictMode": false,                 // Sanitize instead of reject
    "maxQueryComplexity": 100,          // Higher limit for experimentation
    "logValidationAttempts": true
  },
  "otelEnforcement": {
    "enabled": true,
    "validationOnlyMode": true,         // Warn but don't block
    "defaultServiceName": "dev-service",
    "defaultEnvironmentName": "development"
  }
}
```

**For Production**:
```json
{
  "llmBackend": "grafana-llm-app",
  "maxRequestsPerMinute": 60,
  "queryValidation": {
    "enabled": true,
    "enablePromqlValidation": true,
    "enableLogqlValidation": true,
    "enableTraceqlValidation": true,
    "strictMode": true,                                    // Reject invalid queries
    "maxQueryComplexity": 50,
    "allowedFunctions": [
      "rate", "sum", "avg", "max", "min", "count",
      "histogram_quantile", "topk", "bottomk"
    ],
    "logValidationAttempts": true
  },
  "otelEnforcement": {
    "enabled": true,
    "requireServiceName": true,
    "requireEnvironmentName": true,
    "defaultServiceName": "your-service-name",
    "defaultEnvironmentName": "production",
    "rejectIfNoScope": true,                              // Strict enforcement
    "validationOnlyMode": false
  },
  "allowedDatasources": [
    "prometheus-prod-uid",
    "loki-prod-uid",
    "tempo-prod-uid"
  ],
  "defaultDatasource": "prometheus-prod-uid"
}
```

## 📦 Installation

### New Installation

**Via Grafana CLI**:
```bash
grafana-cli plugins install jorgeancal-zagalin-app 0.0.2
```

**Via Docker**:
```bash
docker run -d \
  -p 3000:3000 \
  -e "GF_INSTALL_PLUGINS=jorgeancal-zagalin-app 0.0.2" \
  grafana/grafana:latest
```

**Via Helm (Grafana chart)**:
```yaml
plugins:
  - jorgeancal-zagalin-app 0.0.2
```

**Via Docker Compose** (see `docker-compose.yaml` in repo)

### Upgrade from 0.0.1

```bash
grafana-cli plugins upgrade jorgeancal-zagalin-app
# Restart Grafana
sudo systemctl restart grafana-server
```

**Docker Compose**:
```bash
docker compose down
docker compose pull
docker compose up -d
```

**Kubernetes**:
```bash
kubectl rollout restart deployment/grafana
```

**Recommended Gradual Rollout** (for production):
1. **Week 1**: Enable features in validation-only mode, review logs
2. **Week 2**: Adjust allowlists and defaults based on findings
3. **Week 3**: Enable strict enforcement
